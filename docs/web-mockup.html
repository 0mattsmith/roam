The web interface

What docs/WEB_INTERFACE.md looks like once it is built. A toggle in Settings starts a server on the phone; a laptop on the same wifi gets the library in a browser, with a real keyboard and a screen that fits more than six rows.

1The PIN, once per browser

Not because anyone is attacking you — because “I opened it on my phone by accident and renamed an album” is a real Tuesday. The PIN is shown in Settings beside the address, so there is nothing to work out.

Replacing a cover numbers the outgoing file aside and writes the new one as plain cover.jpg. Nothing on the source is ever destroyed, and the live image always has the same name — so nothing pointing at it has to change.

album.json decides which

"album": "Violator",
"album_artist": "Depeche Mode",
"year": 1990,
"cover_art": "cover.jpg",
"previous_artwork": [
  "cover1.jpg",
  "cover2.jpg"
],
"tracks": [ … ]

A folder holding both cover.jpg and folder.jpg is ordinary. Without the document the ranked filename list decides, which is a guess — so the field outranks it, and both outrank the picture embedded in the tracks.

5Linking a document by hand

The part nothing else does, and the reason a web UI is the right home for it. DocApplier matches on the file locator — never a title or a track number, because those are exactly what an edit changes. Correct, and also why a renamed folder stops matching. With both lists side by side there is somewhere to say this one belongs to that one.

6Where it is turned on

Off by default. The address and the PIN sit together, because needing both and being shown one is the kind of thing that makes a feature feel broken.

Built in this order, each one worth having alone

Stage 1
Browse, read only
Server, PIN, foreground service, library view. Answers the lifecycle question before anything depends on it.
Stage 2
Edit metadata
The actual point. Forms over TrackEditor, dirty-checked.
Stage 3
Cover art
Upload through ArtworkEditor, which archives rather than overwrites.
Stage 4
Link a document
Two lists and a button. Outranks the matcher for good.
Stage 5
Playback, if ever
Range requests over SourceProvider.readRange. Most expensive, least connected to why this is wanted.
Nothing here touches a DAO. Every write goes through TrackEditor and ArtworkEditor — the HTTP layer’s only job is to turn a request into an editor call and the result into JSON. A handler that reached past them would reimplement content-derived ids, the transaction around an album rename and the archive-don’t-overwrite rule, in a place nobody thinks to look.
